# Architecture and operations

How the repository is wired. Pair this with [status.md](status.md).

## Build and dependencies

- C++20, CMake with presets generated by Conan 2, GoogleTest. Warnings are errors
  (`-Wall -Wextra -Wpedantic -Werror`).
- `conanfile.py` has the option `product` (any value, default `productA`). productB adds
  zlib purely so the two lockfiles differ; replace with real product differences.
- Product variants are discovered from `products/`: `<name>.yml`, the product **manifest**,
  plus `<name>.lock` (its lockfile). A `.lock` without `.yml` is ignored with a warning; a `.yml`
  without `.lock` gets one from `conan maturity:lock-update`. The manifest has one section per
  consumer (`options` for the root recipe; `conf`, `targets`, `coverage`, `release` for the
  commands and CI). Every command validates it against a schema in `_maturity.py` (unknown keys
  fail) and merges it over `defaults.yml`, shipped in the config package. `conan maturity:list`
  prints the result, also as JSON for CI. `conf` entries reach the root recipe as
  `user.maturity.product:<key>`; `targets` limits what `lock-update` locks and which `--target`
  the commands accept; `coverage.fail_under` is the default gate of `maturity:coverage`.
- Conan configuration (details and command reference: [conan-commands.md](conan-commands.md)) is
  the configuration package `maturity-config` (`package_type =
  "configuration"`), never files referenced by path. `conanconfig.yml` requests it by range,
  `conan.lock` pins version and recipe revision (`config_requires`), and
  `conan config install-pkg .` installs it (it picks up `conan.lock` automatically). It ships:
  - Profiles on two axes: `maturity/target/<os>-<arch>[-<compiler>]` (compiler detected via
    `detect_api`, `cppstd=20`) and `maturity/build_type/<release|debug>`. Only
    `linux-x86_64` exists; `windows-x86_64`, `linux-armv8`, `relwithdebinfo` are new files.
  - Custom commands in `extensions/commands/maturity/`:
    - `conan maturity:install --product P --target T [--build-type B]` runs `conan install`
      with `products/P.lock`, the product options and the stacked profiles.
    - `conan maturity:build --product P --target T [--build-type B] [--skip-test]` runs
      `conan build` with the same arguments (install, generate, the recipe's `build()`).
      `--skip-test` sets Conan's `tools.build:skip_test=True`: no ctest, `BUILD_TESTING=OFF`.
    - `conan maturity:lock-update [--product P] [--target T]` regenerates product locks over all
      targets and build types and pins the installed config in them.
    - `conan maturity:config-lock-update` re-resolves `conanconfig.yml`, installs the result
      and re-pins it in `conan.lock` and every product lock.
    - `conan maturity:tidy --product P --target T [--diff-base REV] [--fix]` configures
      `build/tidy/Debug` (profile `maturity/tidy`), runs clang-tidy with the project's
      `.clang-tidy` on all project sources (or the changed ones), writes log and SARIF to
      `build/tidy-report/` and fails on findings.
    - `conan maturity:audit [--product P] [--target T] [--severity-level S]` runs
      `conan audit scan` (audit.conan.io) on each product's locked graph, writes JSON, HTML and
      markdown to `build/audit-report/` and fails at the manifest's `audit.severity_level`
      (CVSS 7.0 by default), except for ids accepted with a reason in `audit.ignore`.
    - `conan maturity:coverage --product P --target T [--diff-base REV]` runs `conan build`
      with the profile `maturity/coverage` (consumer-only `--coverage` flags, own build folder
      `build/coverage/Debug`), then gcovr with the project's `gcovr.cfg`, writes the reports to
      `build/coverage-report/` and enforces the line gate (default 90%). Developers and CI run
      the same command.
  - Every product lock carries the config revision too, so `maturity:install` fails
    (`check_lockfile_config`) when the Conan home has a different config installed.
- `.conanrc` sets `conan_home=./.conan2`, so every checkout (for example one per release
  branch) has its own Conan home: its own installed `maturity-config` version, commands,
  profiles and package cache. Conan finds `.conanrc` from any subfolder and it takes
  precedence over `CONAN_HOME`. Dependencies are built once per checkout. CI caches
  `.conan2/p`; the CodeQL job rewrites `.conanrc` to `~/.conan2` so dependency sources stay
  outside the analysed source root.
- `conan-recipes/` is a local-recipes-index (registered as remote `maturity-recipes`) standing
  in for Artifactory. `install-pkg` never builds, so `scripts/conan_bootstrap.sh` builds the
  listed packages from the index first. A checked-in recipe that no longer matches the
  revision in `conan.lock` makes `install-pkg` fail; run `conan maturity:config-lock-update`.
  To split it out: publish the recipe from its own repo, add the remote (or `urls:` in
  `conanconfig.yml`), delete `conan-recipes/` and the bootstrap script. `conanconfig.yml`,
  `conan.lock` and the product locks stay as they are.
- `conan install .` at the root now auto-uses the config-only `conan.lock`; use
  `conan maturity:install` instead.
- Versions come only from release tags. `conanfile.py` has no `version`. `release.yml` derives
  it from the tag (`productA_v1.2.3-rc.1` gives `1.2.3-rc.1`, checked against
  `<major>.<minor>.<patch>[-<pre-release>]`) and runs `conan maturity:build --version`.
  `generate()` sets the cache variable `MATURITY_VERSION` (`0.0.0-dev` without a version), and
  `CMakeLists.txt` uses its numeric part for `project(VERSION)` and the full string for the
  generated `maturity/version.hpp`. `maturity_app --version` prints it. A ctest
  (`maturity_app.version`) and a release step check that the binary reports the expected
  version.
- `conanfile.py` has a standard `build()` (CMake configure, build, `ctest --output-on-failure
  --no-tests=error`), used by `conan build` and so by `maturity:build` and `maturity:coverage`.
  Its `generate()` sets `BUILD_TESTING` from `tools.build:skip_test` both ways: Conan itself
  only sets `OFF`, and a cached `OFF` would otherwise make later builds run stale test binaries.
- The only script left is `conan_bootstrap.sh` (build config packages from the index).
  Building, coverage and clang-tidy are `maturity:*` commands, which `ci.yml`, `codeql.yml`,
  `release.yml`, `coverage.yml` and `clang-tidy.yml` call.
- clang-tidy is pinned as the PyPI wheel `clang-tidy==23.1.3` in
  `.devcontainer/requirements.txt` (not apt), so the devcontainer and CI run the same version;
  Dependabot bumps it.

## Workflows (`.github/workflows/`)

- `ci.yml`: `prek`, `conan-commands` (pytest for the `maturity-config` package), `secrets`
  (betterleaks), and on PRs `dependency-review` (`actions/dependency-review-action`, fails on
  "high" for actions and pip packages; Conan isn't in GitHub's dependency graph).
- `audit.yml`: `conan maturity:audit` for all products, daily (new advisories need no code
  change) and on pushes and PRs that touch the Conan inputs (path filter, to stay within the
  provider's request limit). Uploads `build/audit-report/` (14 days). The token comes from the
  secret `CONAN_AUDIT_TOKEN` as `CONAN_AUDIT_PROVIDER_TOKEN_CONANCENTER`; without it (fork and
  Dependabot PRs) the scan is skipped with a notice. Not a required check, because of the path
  filter.
- `tests.yml`:
  - `products` runs `conan maturity:list --format=json` and outputs the product names.
  - `build-test (<product>, <build type>)` runs for every product in Release and Debug
    (`conan maturity:build`). Each job uploads its single-file test report (14 days) and links
    it from the run summary, plus a `test-summary-*` artifact (`.md`, `.json`).
  - `test-comment` combines them into one sticky PR comment (`<!-- test-comment -->`,
    same-repo non-Dependabot PRs).
  - The **gate** `tests` (`needs: [products, build-test]`, `if: always()`) passes only if every
    matrix job passed. It is the workflow's one required check.
- `coverage.yml`: the same shape:
  - `products`
  - `coverage (<product>)` (job id `coverage-product`, `conan maturity:coverage`, with
    `--diff-base HEAD^1` on PRs for the changed-lines figure). Each job uploads
    `coverage-report-<product>.html` and a `coverage-<product>` artifact (summary, XML,
    `tests-coverage-<product>.html`, line percent).
  - `coverage-comment` (one sticky comment, a section per product)
  - the gate `coverage`
- **Adding a product** (`products/<name>.yml`) needs no workflow or ruleset change: `products`
  picks it up, and the gates cover its jobs. Only its `release-<name>.yml` caller is new, because
  tag triggers can't be generated. Matrix job outputs overwrite each other, so the comment jobs
  read artifacts (`actions: read`). Neither workflow has a `paths:` filter: their gates are
  required checks, and a skipped required check counts as passing.
- `clang-tidy.yml`: `conan maturity:tidy` (pinned clang-tidy from `requirements.txt`), uploads
  the SARIF to code scanning, fails on any finding.
- `codeql.yml`: CodeQL (`analyze (c-cpp)`). `scorecard.yml`: OpenSSF Scorecard.
- `release.yml`: reusable (`workflow_call`, input `product`). `release-productA.yml` and
  `release-productB.yml` trigger on `productA_v*` / `productB_v*`, grant
  contents/id-token/attestations write, and call it. It checks the tag matches the product,
  builds, packages, produces a coverage HTML (`maturity:coverage` for the product), the test
  report of the product (`maturity-<tag>-tests.html`) and a CycloneDX SBOM from the product
  lockfile, attests them, and creates the GitHub release (pre-release if the version has a hyphen;
  `--latest`/`--latest=false` from the manifest's `release.latest`, nothing when `null`).
  Verify with `gh attestation verify <file> --repo mariusheise/software-maturity
  --signer-workflow mariusheise/software-maturity/.github/workflows/release.yml`.

## Repository settings (not in git)

- Ruleset `protect-main` (id 25796571): default branch; no deletion, no force-push, linear
  history, signed commits, PR required, 7 required status checks: prek, tests, coverage,
  conan-commands, secrets (betterleaks), analyze (c-cpp), clang-tidy. `tests` and `coverage`
  are the gate jobs, so the list doesn't change when products are added.
  Repo admin may bypass via PR (own PRs are admin-merged after CI passes). Squash-merge only.
- One repository secret, `CONAN_AUDIT_TOKEN` (audit.conan.io token for `audit.yml`). No
  environments or repository variables. The badge setup (gist, `COVERAGE_GIST_ID`, environment
  `coverage-badge`, `GIST_TOKEN`) was deleted with the badges (see "Badges (planned)").
- Dependabot is configured (`.github/dependabot.yml`).

## Badges (planned, not built)

The README has no badges. The earlier ones sent data to third parties, which a commercial
product must not do:
- shields.io fetched the values on every page view, and it can't read private repositories.
- The "secret" gist behind them is only unlisted: anyone with its URL, which was in the README,
  could read it.
- The OpenSSF Scorecard badge only exists for public repositories.

The planned design keeps everything inside GitHub:

1. `conan maturity:badge --label L --message M --color C --output F` in the config package
   renders a flat SVG with the standard library only (escaped text, width estimated per
   character).
2. On push to `main`, a badge job in `coverage.yml` and in `tests.yml` reads the existing
   artifacts (`line-percent-productA.txt`, the `test-summary-*` totals). It renders
   `coverage.svg` and `tests.svg` and commits them to an orphan branch `badges`
   (`contents: write`). `protect-main` covers only the default branch. All badge jobs share
   the concurrency group `badges` (`cancel-in-progress: false`) and push with a
   fetch-and-rebase retry.
3. The release `publish` job renders `release-<product>.svg` (the version; a different colour for
   pre-releases) into the same branch.
4. The README shows them by relative path, `![coverage](../../raw/badges/coverage.svg)`. GitHub
   serves these through `github.com/<owner>/<repo>/raw/…` with the viewer's session, so members
   of a private repository see them and nobody else does. Release badges link to
   `../../releases?q=<product>_v`.


## CI hygiene rules

SHA-pinned actions, least-privilege `permissions` (top-level `{}`), concurrency groups,
untrusted values only via `env:`. Zizmor ignores the `self-repository` rule for the
caller workflows (`.github/zizmor.yml`). Coverage is gated at 90% lines; `src/main.cpp` is excluded (`gcovr.cfg`).

## Working environment notes

- Develop inside the devcontainer; `gh`, `jq`, gcovr and the pinned clang-tidy are available
  there, not necessarily on the host. Every tool, its pin and what updates it:
  [dependencies.md](dependencies.md). After a change to `.devcontainer/requirements.txt`,
  rebuild the container: `/opt/venv` belongs to root, so `pip install` fails without it.
- Claude Code keeps its state in the Docker volume `software-maturity-claude`, mounted at
  `~/.claude` with `CLAUDE_CONFIG_DIR` pointing there. Sessions, memory, settings
  (`.claude.json`) and login survive rebuilds. `docker volume rm software-maturity-claude`
  resets them.
- GitHub signs squash merges; tags pushed from the container are lightweight
  (no GPG key there).
- `actions/upload-code-coverage` and GitHub Code Quality need a Team/Enterprise plan; the
  trial (PR #22) was closed. The coverage report is a 14-day workflow artifact (PR runs)
  and a permanent download on releases.
